2. DEPLOYMENT COMPLEXITY ASSESSMENT
------------------------------------------------------------------------------
- Official Docker image: NONE. All images are community-maintained.
- Database requirement: MySQL/MariaDB ONLY. No PostgreSQL support in v1.x.
- SupportPlane cluster topology: PostgreSQL-only (no MySQL/MariaDB present).
- Kubernetes deployment would require:
  a) New MySQL/MariaDB StatefulSet + PVC + Secret + Service
  b) Web/PHP-FPM container (unofficial image)
  c) Separate cron container (some images split this out)
  d) Web-based setup wizard (not fully automatable)
  e) Ingress/Service configuration
- Estimated setup effort: 2–4 hours local; ongoing maintenance burden is
  non-trivial due to unofficial image and PHP version compatibility tracking.
- Comparison: Zammad has an official image, init-container pattern, and fits
  neatly into a StatefulSet. osTicket does not.

------------------------------------------------------------------------------
3. API CAPABILITY SUMMARY
------------------------------------------------------------------------------
Supported HTTP API operations in osTicket v1.x:
  POST /api/tickets.json   -> Create ticket
  POST /api/tickets.xml    -> Create ticket
  POST /api/tickets.email  -> Create ticket via email
  POST /api/tasks/cron     -> Trigger cron

UNSUPPORTED operations (not exposed by official API):
  GET  /api/tickets        -> NOT AVAILABLE
  GET  /api/tickets/{id}   -> NOT AVAILABLE
  GET  /api/users          -> NOT AVAILABLE
  GET  /api/customers      -> NOT AVAILABLE

Authentication: API keys tied to source IP address. Fragile in Kubernetes
environments with ephemeral pod IPs unless reverse-proxied with
X-Forwarded-For trust.

Gap vs. SupportPlane adapter contract:
  OsTicketAdapterFactory.capabilities = ['read_tickets', 'read_customers']
  osTicket v1.x API can satisfy NEITHER capability.

------------------------------------------------------------------------------
4. RECOMMENDATION WITH HONEST RATIONALE
------------------------------------------------------------------------------
VERDICT: BLOCK BL-128. Keep as blocked/planned.

Rationale:
1. osTicket v1.x has no read API. It is fundamentally impossible to implement
   the SupportPlane read-ticket and read-customer integration against the
   official API today.
2. osTicket v1.x requires MySQL/MariaDB. SupportPlane uses PostgreSQL
   exclusively. Adding a second RDBMS engine is out of scope and increases
   operational surface.
3. No official container image exists. Relying on unmaintained community
   images introduces supply-chain and security-update risk.

These are not configuration issues or missing documentation — they are
architectural limitations of the upstream product in its current stable
release.

Conditions for unblocking:
- osTicket 2.0 reaches GA with verified GET endpoints for tickets/users AND
  official PostgreSQL support AND an official container image, OR
- An alternative integration path (e.g., plugin exposing read REST API) is
  discovered and vetted.

Next step:
- Retain the existing fixture-backed OsTicketAdapterFactory stub.
- Do not allocate implementation time to a real osTicket integration until
  upstream blockers are resolved.
